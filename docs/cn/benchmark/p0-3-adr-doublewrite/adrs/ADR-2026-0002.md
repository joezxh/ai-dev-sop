## 1. 背景与问题陈述

业务平台内部模块间事件通信存在三种方式：Spring ApplicationEvent（进程内）、HTTP 调用（同步阻塞）、Kafka 主题（无统一规范）。需收敛。

## 2. 决策驱动因素

- **业务驱动**：跨服务事务、事件追溯、审计要求
- **技术驱动**：解耦、可观测、可重放
- **约束**：业务侧零侵入

## 3. 备选方案

### 方案 A：维持现状（被拒）
- 缺点：一致性差、追溯难

### 方案 B：Kafka + 统一事件框架（被选 ✅）
- 优点：成熟生态、公司已有 Kafka 平台
- 缺点：需统一 schema、跨服务 schema 治理
- 成本估算：1 人 / 4 周

### 方案 C：EventBridge 自研
- 优点：完全可控
- 缺点：重复造轮子、维护成本高
- 成本估算：2 人 / 12 周

## 4. 决策

**采纳方案 B · Kafka + 统一事件框架（adsop-event-bus）**。

所有事件 schema 在 `adsop-module-eventbus/contract/` 下用 Avro 定义，向后兼容。

## 5. 后果与影响

### 5.1 代码影响
- 新增：`adsop-module-eventbus`（事件框架）
- 新增：`adsop.module.order.event.OrderPaidEvent`（首个迁移事件）
- 新增：`adsop.module.notify.listener.OrderPaidListener`（消费方）
- 修改：`adsop.module.order.service.OrderService.markPaid`（改 EMITS）

### 5.2 性能 / 成本影响
- 性能：异步事件端到端 P99 < 50ms
- 成本：复用公司 Kafka 平台，0 额外费用

### 5.3 风险与缓解
| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| Schema 演进 | 中 | Avro 向后兼容 + schema registry |
| 事件丢失 | 低 | Kafka acks=all + 幂等消费者 |
| 顺序问题 | 中 | partition key = 业务主键 |

## 6. 回滚方案

业务侧可降级为同步 HTTP 调用（保留 fallback）。
