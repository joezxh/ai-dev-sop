## 1. 背景与问题陈述

Qdrant 集群上线 1 年后，运维成本显现：
- 独立集群（3 节点）+ 备份/监控/告警自成体系
- 双写问题：业务数据在 PG，向量在 Qdrant，跨库事务难
- SRE 投入：每周 0.5 人天

2026 Q1 评估 PGVector 后，确认性能 / 功能 / 运维三者可兼顾。

## 2. 决策驱动因素

- **业务驱动**：减少跨库事务、提升一致性、降低运维成本
- **技术驱动**：PG 16 + pgvector 0.7 + HNSW 索引已生产可用
- **约束**：需 4 周内切换，业务无感

## 3. 备选方案

### 方案 A：PGVector（被选 ✅）
- 优点：与业务数据同库 / 事务一致 / 零额外运维 / pgvector 0.7 HNSW 性能已对标专用向量库
- 缺点：写入吞吐略低于专用向量库（实测 5000 vec/s，仍 ≥ 业务峰值 200 vec/s × 10）
- 成本估算：原 PG 实例升级 2C4G / 月 ≈ +¥600

### 方案 B：维持 Qdrant
- 优点：性能最优
- 缺点：运维成本、双库事务、SRE 投入持续
- 成本估算：维持 ¥1800/月 + SRE 0.5 人天/周

### 方案 C：迁移到 Milvus
- 优点：功能更全
- 缺点：迁移成本高、运维更重
- 成本估算：≥ ¥5400/月

## 4. 决策

**采纳方案 A · PGVector**。

理由：在性能已达业务阈值的前提下，**运维简化 + 事务一致性**的收益远超性能边际。

## 5. 后果与影响

### 5.1 代码影响
- 新增：`adsop.module.kms.config.VectorStoreConfig`（PGVector Bean）
- 新增：`adsop.module.kms.service.VectorStoreService`（PGVector 客户端）
- 新增：`adsop.module.kms.dao.VectorStoreMapper`（MyBatis 映射）
- 删除：`adsop.module.kms.vectorstore.qdrant_client.*`
- 删除：`docker-compose.qdrant.yml`
- 修改：`adsop.module.case.service.CaseSearchService`（调用 VectorStoreService）

### 5.2 性能 / 成本影响
- 性能：查询 P99 = 180ms（vs Qdrant 120ms，业务可接受）
- 写入吞吐：5000 vec/s（业务峰值 200 vec/s）
- 成本：**月省 ¥1200 + SRE 投入 -0.5 人天/周**

### 5.3 风险与缓解
| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| PGVector 大表膨胀 | 中 | 周级 VACUUM + 季度分区 |
| HNSW 内存占用 | 中 | PG shared_buffers 升级 + 监控 |
| 回滚路径 | 低 | 旧 Qdrant 数据保留 30 天 |

## 6. 回滚方案

1. 停 PGVector 写入
2. feature flag 切回 Qdrant
3. 从备份恢复 Qdrant 数据
4. 回滚预计耗时 2 小时
