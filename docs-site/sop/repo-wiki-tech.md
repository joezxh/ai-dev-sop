# Qoder 两步蒸馏法（Two-Step Distillation）完整详解
两步蒸馏法是 Qoder Knowledge Engine 2.0 的核心技术方法论，基于「编译式知识（Compiled Knowledge）」理念设计，核心是解决**机器检索与人类阅读对知识形态的需求冲突**，是 Repo-Wiki 与 Agent 编码能力的底层支撑。

## 一、设计背景与核心本质
### 1. 传统方案的本质矛盾
在两步蒸馏法出现之前，代码知识库的主流方案是「原始代码 → 直接生成 Wiki 文档」的单次生成模式。但同一份产物同时服务两类消费者时，必然顾此失彼：
- **AI Agent 需要**：高密度、结构化、单一职责、可精准定位的信号，不需要叙事性铺垫，检索时要一击即中
- **人类开发者需要**：连贯、成体系、有逻辑脉络的叙事文档，需要上下文衔接与整体认知，不需要碎片化键值对

Qoder 官方明确指出：一份产物同时满足两种需求，最终只会两头都做不好。

### 2. 两步蒸馏的核心思路
两步蒸馏法将「知识生产」拆成两个独立阶段，分别产出对应两类消费者的产物，实现需求解耦：
1. **第一步蒸馏（Distill #1）**：把零散的原始代码信号，编译成面向 Agent 消费的 **Knowledge Cards（知识卡片）**——结构化、高密度、可检索
2. **第二步蒸馏（Distill #2）**：把结构化的知识卡片，蒸馏成面向人类阅读的 **Repo Wiki**——叙事化、体系化、易理解

整个过程对应禅宗「见山三阶段」的认知逻辑，官方称之为知识的三重境界。

## 二、第一步蒸馏：原始信号 → Knowledge Cards
### 1. 核心定位
第一步是「知识编译」阶段：将非结构化、高熵的原始代码信息，转化为机器可直接消费的结构化知识单元，相当于把代码“编译”成知识字节码。这一步只提取客观事实，不做叙事化加工。

### 2. 输入源
全量原始项目信号，包含四类高熵素材：
- 源代码文件（受 `.gitignore` 过滤）
- Git 提交记录与变更历史
- 历史查询与对话日志
- 项目规格文档（Spec/Plan）

### 3. 完整处理流程
1. **静态代码结构化解析**
  - 词法/语法分析：构建 AST 抽象语法树，建立符号表
  - 实体提取：识别所有模块、类、接口、函数、配置项、常量等代码实体
  - 依赖建模：基于 import、调用、继承关系生成有向依赖图谱
  - 架构识别：通过社区发现算法推断模块边界与架构风格（分层、事件驱动、插件化等）

2. **知识切片与分类**
   按照单一职责原则，将代码信息拆分为不同类型的独立知识单元，每张卡片只覆盖一个主题，避免信息混杂。标准卡片类型包括：
   | 卡片类型 | 核心内容 | 核心作用 |
   |---------|---------|----------|
   | 架构总览卡 | 项目类型、架构风格、模块划分、核心链路 | 让 Agent 快速建立项目全局认知 |
   | 技术栈卡 | 语言版本、框架、中间件、核心依赖与用途 | 约束生成代码的环境兼容性 |
   | 代码规范卡 | 命名约定、设计规约、异常处理规则 | 保证 Agent 输出符合项目风格 |
   | 核心模块卡 | 单模块的职责、入口方法、对外接口 | 精准定位业务逻辑位置 |
   | 数据模型卡 | 实体定义、表结构、枚举值、关系映射 | 统一数据结构认知 |
   | 配置项卡 | 环境参数、启动开关、配置说明 | 避免配置类错误 |

3. **结构化压缩与溯源标注**
  - 去除冗余代码文本，仅保留核心事实（职责、签名、约束、依赖），最大化信息密度
  - 每条信息都标注代码溯源：文件路径 + 行号范围，确保所有结论可验证
  - 为每张卡片生成唯一 ID 与版本号，用于后续关联与增量更新

### 4. 产物特征
- **面向 Agent 设计**：优先信息密度与机器可读性，而非人类阅读体验
- **强结构化**：以键值对、列表格式为主，无冗余叙事性文字
- **单一职责**：一张卡片只解决一个维度的问题，检索时无噪声
- **可溯源**：所有信息均可映射回具体代码行，从源头控制幻觉
- **可复用**：是整个知识引擎的公共底座，问答、代码生成、调试、Wiki 生成等所有 Agent 场景均复用该层数据

## 三、第二步蒸馏：Knowledge Cards → Repo Wiki
### 1. 核心定位
第二步是「知识叙事化」阶段：将碎片化的结构化知识卡片，重组为连贯、成体系、符合人类阅读习惯的技术文档。这一步不产生新的事实，只做逻辑串联、叙事组织与表达优化。

### 2. 输入源
- 全量 Knowledge Cards 结构化数据
- 模块依赖图谱、调用链路元数据
- 项目类型匹配的文档结构模板

### 3. 完整处理流程
1. **文档架构规划**
   根据项目类型（后端服务/前端应用/工具库/中间件）自动匹配 Wiki 章节模板，设计分层目录结构，明确每个章节对应的知识卡片来源，保证章节粒度均匀、逻辑从总览到细节递进。

2. **分章节叙事生成**
   每个章节独立生成，以对应主题的知识卡片为唯一事实依据，完成从「结构化碎片」到「连贯文档」的转化：
  - 补充逻辑衔接语，将孤立知识点串联成完整叙事
  - 梳理模块间的协作关系、业务流转逻辑
  - 基于依赖数据生成 Mermaid 架构图、流程图、时序图
  - 补充设计背景与选型说明，提升文档的可理解性

3. **交叉校验与溯源增强**
  - 校验文档内容与知识卡片的事实一致性，杜绝无依据的脑补
  - 为关键设计点、接口定义保留代码溯源链接，支持一键跳转到源码
  - 统一全文档的术语、命名风格与表述口径

4. **整体润色与导航生成**
   生成全局目录、章节跳转、快速入门指引，补充项目总览与阅读建议，形成完整的 Wiki 文档体系。

### 4. 产物特征
- **面向人类设计**：优先可读性、逻辑性与体系感，适合开发者快速上手项目
- **叙事化表达**：有完整的上下文与逻辑脉络，不是知识点的简单堆砌
- **分层递进**：从总览到细节、从入门到深入，符合人类的认知规律
- **二次蒸馏产物**：并非直接从代码摘抄生成，而是经过知识卡片的中间提炼，信息纯度更高、冗余更少
- **标准章节体系**：通常包含项目概览、快速开始、架构设计、核心模块、API 参考、数据模型、开发规范、部署运维八大核心章节

## 四、知识的三重境界：官方认知模型
Qoder 官方用「见山三阶段」的禅宗比喻，对应两步蒸馏法的完整认知链路，解释知识形态的三次跃迁：
1. **第一重：见山是山 —— 原始信号阶段**
   原材料是零散、孤立的代码行、提交记录、文档，高熵且无序。此时看到的只是代码文本本身，看不到系统的整体逻辑与设计。

2. **第二重：见山不是山 —— 第一步蒸馏完成**
   具象的代码文本被抽象成结构化的知识卡片，脱离了原始代码的物理形态，变成了机器可理解的知识信号。它不再是“代码”，而是提炼后的结构化知识，是认知的抽象跃迁。

3. **第三重：见山还是山 —— 第二步蒸馏完成**
   结构化的知识碎片被重新组织成完整的项目认知体系，再次回到“项目全貌”的形态。但此时的“山”是经过梳理、提炼、结构化的完整认知，而非最初零散混乱的代码堆砌。

## 五、与传统方案的核心差异
### 1. 对比传统「代码→Wiki」单次生成
| 维度 | 传统单次生成 | Qoder 两步蒸馏法 |
|------|--------------|------------------|
| 产物形态 | 单份文档同时服务人和机器 | 两层独立产物，分别匹配两类消费者 |
| 事实准确性 | 直接从代码生成，易出现幻觉与脑补 | 第一步先固化客观事实，第二步只做叙事，幻觉率大幅降低 |
| 检索效率 | 文档片段冗余多，检索噪声大 | 知识卡片高密度结构化，Agent 检索一击即中 |
| 增量成本 | 代码变更需重生成整段/整篇文档 | 仅更新对应卡片，再增量刷新 Wiki 段落，成本极低 |
| 知识复用 | 文档仅能用于阅读，无法被 Agent 直接消费 | 知识卡片是公共底座，所有 AI 场景均可复用 |

### 2. 对比传统 RAG 方案
传统 RAG 的逻辑是「每次查询都重新切分、检索、拼接答案」，知识永远处于“每次重新发现”的状态；而两步蒸馏法属于**编译式知识范式**：一次编译、永久复用、持续沉淀，知识会随着项目演进而不断积累加厚，而非每次查询都从零开始。

## 六、配套的自迭代增量机制
两步蒸馏法并非一次性流程，而是与 Git 开发流程联动的自循环体系：
1. **触发条件**：Git HEAD 发生变更（代码提交后）自动触发
2. **更新链路**：解析 git diff → 定位受影响的代码实体 → 刷新对应 Knowledge Cards → 增量更新 Repo Wiki 中关联的章节段落
3. **核心原则**：最小影响范围，只修改与变更直接相关的内容，不做全量重生成
4. **双向补充**：除了代码侧的自动更新，开发者与 Agent 对话中的决策、踩坑经验、设计意图，也会通过 Memory 机制反向沉淀到知识体系中，补充代码无法直接体现的隐性知识

---

## 七、核心设计价值
1. **需求彻底解耦**：从根源上解决了「机器检索效率」与「人类阅读体验」对知识形态的矛盾要求，两类场景都能达到最优解。
2. **质量分层可控**：将「事实准确性」和「表达可读性」拆分到两个阶段控制，第一步严格约束客观事实，第二步专注表达优化，大幅降低 LLM 幻觉。
3. **知识资产沉淀**：知识卡片作为可复用的底层资产，避免了每个 AI 功能都重复解析代码的冗余，让项目知识越用越准。
4. **解决文档过期难题**：增量更新机制让文档与代码自动同步，解决了传统技术文档“写完就过时”的行业痛点。
